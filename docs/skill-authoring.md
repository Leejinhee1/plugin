## 1. 루트 가치: 예측가능성 (Predictability)

스킬은 확률적 시스템(LLM)에서 결정론을 끌어내기 위해 존재한다. **매 실행마다 같은 과정을
밟는 것이 목표다 — 같은 출력이 아니라.** 입력이 다르면 출력도 달라야 정상이지만, "이번엔
registry.json을 먼저 조회했는데 저번엔 안 했다" 같은 절차 편차는 스킬의 존재 이유를 지운다.

HDS 실례 — `hds-planning/skills/grill/SKILL.md`:
> "질문은 **한 번에 하나만** 한다. 다음 질문은 답을 받은 뒤에 던진다."
> "질문 축 (이 순서로 내려간다): 1. Why → 2. 범위 → 3. 화면·상태 → 4. 엣지케이스"

내용(질문 자체)은 매번 다르지만 **절차**(순서·한 번에 하나씩)는 항상 같다. 이것이
예측가능성이다.

| 판단 기준 | 물어볼 질문 |
| :-- | :-- |
| 절차 고정 | 이 스킬을 5번 실행하면 5번 다 같은 순서로 움직이는가? |
| 근거 우선 | 판단이 필요한 지점마다 "무엇을 먼저 조회하는가"가 명시돼 있는가? |
| 재현 가능 | 다른 사람이 같은 입력으로 실행해도 같은 결론에 도달하는가? |

## 2. model-invoked vs user-invoked

스킬은 두 가지 방식으로 켜진다. **model-invoked**(기본값)는 `description`을 Claude가 항상
읽고 판단하므로 **매 세션마다 컨텍스트 비용**을 지불한다 — 대신 사람이 스킬 이름을 몰라도
자동 발동된다. **user-invoked**(`disable-model-invocation: true`)는 컨텍스트 비용이 0이지만
사람이 `/plugin:skill`로 직접 불러야 하므로 **존재를 기억해야** 한다.

현재 HDS의 12개 스킬은 모두 model-invoked다(자연어 호출을 1급 시나리오로 삼기 때문 —
`docs/user-guide.md`: "자연어로 물어도 Claude가 알아서 해당 스킬을 사용합니다"). 새 스킬을
추가할 때는 아래 표로 유지할지 전환할지 판단한다.

| 기준 | model-invoked 유지 | user-invoked 전환(`disable-model-invocation: true`) 검토 |
| :-- | :-- | :-- |
| 호출 빈도 | 파트 업무 중 자연스럽게 반복 등장 (예: 토큰 조회) | 릴리스·마이그레이션처럼 드물고 의도적인 순간에만 |
| 부작용 크기 | 조회·초안 생성 등 되돌리기 쉬움 | 파일 대량 생성/설치처럼 실수로 자동 발동되면 곤란 (`component-build`가 후보) |
| 트리거 모호성 | 자연어 문장과 1:1로 매칭됨 | 다른 스킬과 트리거가 겹쳐 오발동 위험이 큼 |
| 사용자 숙련도 | 스킬 이름을 몰라도 되는 초심자 대상 | 반복 사용하는 숙련자 전용 도구 |

전환 시 `docs/user-guide.md`의 해당 시나리오에 `/hds-x:skill` 명시 호출 예시를 반드시 남겨
"기억해야 하는 부담"을 문서가 대신 지게 한다.

## 3. description 작성법

**트리거 단어를 문장 맨 앞에 둔다.** Claude는 description을 훑어 발동 여부를 판단하므로,
핵심 동사·명사가 뒤에 있으면 스캔에서 밀린다. **브랜치(의미 갈래)당 트리거 1개** — 같은
뜻의 동의어를 나열하는 건 신호가 아니라 중복이다.

좋은 예 — `hds-design/skills/design-tokens/SKILL.md`:
```
description: HDS 디자인 토큰(색·타이포·간격·모션)을 조회·추가·수정합니다.
토큰 값을 바꾸거나, 새 semantic 토큰을 추가하거나, 특정 UI에 어떤 토큰을
써야 하는지 물을 때 사용. Use when adding/editing design tokens or
choosing which token applies.
```
"조회·추가·수정"이 맨 앞에서 세 가지 서로 다른 브랜치(읽기/쓰기/판단)를 각 1개 동사로
커버한다. 동의어를 겹쳐 쓰지 않았다.

나쁜 예(가상): "토큰과 관련된 다양한 작업을 도와주는 스킬입니다. 색상, 색깔, 컬러 값을
바꾸거나 조정하거나 변경하고 싶을 때 사용하세요." — "바꾸거나/조정하거나/변경"과
"색상/색깔/컬러"는 같은 브랜치의 동의어 반복이며, 트리거가 문장 앞이 아니라 뒤에 있다.

## 4. 정보 위계 3단 (progressive disclosure)

같은 정보를 세 층 중 어디에 둘지는 **"몇 번의 실행마다 다시 읽어야 하는가"**로 정한다. 위에
너무 두면 본문이 비대해져 매번 로드되고, 아래로 너무 내리면 필요한 순간에 안 보인다.

| 층 | 위치 | 로드 시점 | HDS 실례 |
| :-- | :-- | :-- | :-- |
| 1. 본문 스텝 | `SKILL.md` 자체 | 스킬 발동 시 항상 | `component-catalog`의 "새 컴포넌트 추가 (3종 세트 + 등록)" 6단계 — 매번 필요한 절차라 본문에 둠 |
| 2. 스킬 내 참조 파일 | 스킬 폴더 하위 (`templates/`, `checklist.md` 등) | 본문이 지목할 때만 | `product-spec`의 `templates/spec-template.md` — 매 실행 로드하지 않고 "복사해 시작" 시점에만 읽음 |
| 3. 외부 문서 경로 | 플러그인 밖 SoT (`design-system/...`) | 조회가 필요한 그 작업에서만 | `design-tokens`가 본문에서 `core.tokens.json`/`semantic.tokens.json` 경로만 가리키고 내용을 복사해 넣지 않음 |

새 스킬에 체크리스트·표·긴 예시가 필요하면 먼저 "이게 매번 필요한가?"를 묻는다. 아니라면
`references/` 나 `templates/` 하위 파일로 내리고 본문에는 "언제 이 파일을 열어야 하는지"
한 줄만 남긴다.

## 5. 리딩 워드 (leading word)

모델이 이미 알고 있는 **압축된 개념 하나**를 반복해서 쓰면, 긴 설명 없이도 적은 토큰으로
행동을 고정할 수 있다. 절차를 매번 풀어 쓰는 대신 하나의 단어/구절에 실어 나른다.

HDS 실례:
- `product-spec`의 **"합성만(재인터뷰 금지)"** — "grill에서 나온 결정을 다시 묻지 않고
  문서 형식으로만 옮긴다"는 긴 규칙을 "합성만"이라는 한 단어에 압축.
- `spec-review`의 **"구체성 검사(Specificity over vibes)"** — 매번 "제네릭 표현을 찾아
  구체적 토큰/컴포넌트 이름으로 바꿔라"를 다시 설명하지 않고 이 표제어로 호출.
- `grill`의 **"한 번에 하나만"** — 다단계 인터뷰 규율 전체를 네 글자로 고정.

새 스킬을 쓸 때 반복되는 규칙이 보이면, 그 규칙에 짧은 이름을 붙이고 본문 전체에서 그
이름만 일관되게 재사용한다.

## 6. 실패 모드 6종과 처방

| 실패 모드 | 증상 | HDS 맥락의 처방 |
| :-- | :-- | :-- |
| **Premature completion** | 스킬이 절반만 하고 "완료"라 답함 | 완료 기준을 날카롭게: `spec-review`처럼 "10점이거나 사용자가 멈출 때까지 반복"으로 종료 조건을 수치·조건으로 명시 |
| **Duplication** | 같은 사실을 두 곳에 다르게 서술 (단일 소스 위반) | HDS에선 `registry.json`·`tokens/*.json` 내용을 스킬 본문에 다시 옮겨 적지 않는다. `design-tokens`처럼 "원본은 언제나 tokens/"라고 경로만 가리킴 |
| **Sediment** | 옛 버전 지시가 안 지워지고 쌓여 서로 모순 | 토큰/컴포넌트 값이 바뀌면 스킬 본문이 아니라 SoT(`design-system/`)가 바뀌므로, 스킬 본문에 구체적 값을 하드코딩하지 않는다 |
| **Sprawl** | 본문이 길어져 매번 다 읽어야 함 | §4 정보 위계로 레이어 2/3에 내리기. 이 저장소 스킬은 대부분 30줄 내외를 유지 |
| **No-op** | 모델이 지시 없이도 어차피 하는 행동을 지시로 적음 ("친절하게 답하세요" 류) | 스킬에는 HDS 고유의 절차·SoT 경로·판단 기준만 남기고, 일반 상식 지시는 뺀다 |
| **Negation** | "~하지 마세요"만 적으면 그 행동이 오히려 모델의 사고에 활성화됨("코끼리를 생각하지 마") | 금지형 대신 원하는 행동을 긍정형으로 서술. `design-tokens`의 좋은 예: "컴포넌트 코드나 export 산출물을 직접 고치지 말 것"에 그치지 않고 바로 "원본은 언제나 tokens/"라는 긍정 대안을 붙임 |

나쁜 예(가상, Negation): "토큰 검색을 서두르지 마시오." → "서두름" 개념만 심어줄 뿐 대안이
없다. 대신: "검색 결과 상위 3개 후보를 제시하고 각각의 근거(role·contrast)를 든다."

## 7. HDS 체크리스트 (새 스킬 PR 전)

- [ ] 프론트매터에 `name`, `description`만 있고 불필요한 필드가 없는가
- [ ] `description`이 트리거 단어로 시작하고, 브랜치별 동사가 1개씩인가(동의어 나열 없음)
- [ ] `description`에 한국어 트리거와 영어 트리거("Use when...")가 모두 있는가
- [ ] 반복 로드가 불필요한 내용(체크리스트·템플릿·긴 표)은 스킬 폴더 하위 참조 파일로
      분리했는가(§4)
- [ ] 본문이 SoT(`design-system/`, `registry.json` 등)의 내용을 복사하지 않고 경로만
      가리키는가(Duplication 방지)
- [ ] 이 스킬이 어떤 스킬 뒤에 오고 어떤 스킬로 이어지는지 "산출 후"/"시작 전" 절에 명시했는가
      (예: `grill` → `product-spec` → `spec-review` → `handoff`)
- [ ] `docs/user-guide.md`에 해당 파트 시나리오(호출 예시 1개 이상)를 추가했는가
- [ ] model-invoked 유지 여부를 §2 표로 판단했는가(부작용이 크면 user-invoked 검토)
- [ ] `CHANGELOG.md` 기록 + 해당 `plugin.json`/`marketplace.json` version bump
- [ ] `claude plugin validate <plugin> --strict` 통과
