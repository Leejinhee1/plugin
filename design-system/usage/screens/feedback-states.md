# 공통 상태 패턴 (empty / loading / error)

특정 화면 유형이 아니라, 어느 화면에서든 반복되는 세 가지 상태(비어 있음·로딩 중·오류)를 다루는 규칙 모음. `login.md`, `list-detail.md`, `form.md`는 이 문서를 인용해 상태를 구현한다.

## 목적

- 비어 있거나 실패한 화면에서도 사용자가 다음에 무엇을 해야 할지 항상 알 수 있게 한다.
- 로딩 중임을 시각적으로 명확히 알려 "멈춘 화면"으로 오해하지 않게 한다.
- 세 상태 모두에서 동일한 카피 톤(차분한 존댓말, 과장 없는 사실 전달)을 유지해 브랜드 신뢰를 지킨다.

## 구성 (컴포넌트 + 레이아웃)

### Empty (빈 상태)

콘텐츠 영역 전체를 대체하는 안내 블록. 목록/리스트 영역 중앙에 배치.

```
[ 안내 문구 (body, fg.muted) ]  ← space.stack-md
[ Button variant=primary (다음 행동 제안) ]
```

- 안내 문구는 `typography.body` + `color.fg.muted`. 죄책감이나 부담을 주는 표현 금지("아직 아무것도 안 하셨네요" 같은 지적조 금지).
- 카피 규칙(voice-tone `빈 상태` 톤 근거):
  - 상태를 있는 그대로 말한다: "아직 등록된 일정이 없어요."
  - 바로 이어서 다음 행동을 제안한다: "첫 일정을 추가해 볼까요?"
  - 느낌표·이모지 금지, 해요체 유지.
- 다음 행동이 명확한 경우(대부분) `Button`(`variant="primary"`)을 함께 배치해 안내에서 끝나지 않고 행동으로 연결한다. 다음 행동이 없는 순수 정보성 빈 상태(예: 알림 없음)는 버튼 없이 문구만 노출해도 된다.
- 검색·필터 결과가 없는 경우는 "생성"이 아니라 "조건 변경"이 다음 행동이므로 문구를 다르게 쓴다: "조건에 맞는 일정이 없어요. 필터를 바꿔보세요." — Button 없이 텍스트 안내만으로 충분한 경우가 많다.

### Loading (로딩 중)

콘텐츠 유형에 따라 두 가지 방식을 구분해 쓴다.

| 상황 | 방식 |
| :-- | :-- |
| 목록·카드처럼 레이아웃 구조를 미리 아는 콘텐츠 | 스켈레톤 |
| 버튼 클릭 등 짧고 즉각적인 액션 진행 | 스피너(컴포넌트 내장 `loading` prop) |

- **스켈레톤**: `Card`와 동일한 반경(`dimension.radius.lg`)·안쪽 여백(`space.inset-md`)을 가진 회색 블록을 실제 콘텐츠 개수만큼(보통 2~3개) 배치해 레이아웃이 로딩 완료 후 갑자기 흔들리지 않게 한다. 스켈레톤은 실제 텍스트를 흉내 낸 굵기 다른 블록(제목 줄은 굵게/짧게, 본문 줄은 얇게/길게)으로 구성한다.
- **스피너(버튼 내장)**: 폼 제출, 저장, 재시도처럼 사용자가 직접 트리거한 단발성 액션에는 `Button`의 `loading={true}` prop을 쓴다. 별도 스피너 컴포넌트를 화면에 새로 만들지 않는다 — Button 스펙에 이미 정의되어 있다(`aria-busy`, 클릭 차단 자동 처리).
- 기준: 로딩이 300ms 미만으로 끝날 것으로 예상되면 굳이 스켈레톤을 보여줄 필요는 없다(깜빡임 방지). 1초 이상 걸릴 수 있는 목록 로딩은 반드시 스켈레톤을 노출한다.
- 로딩 중에는 관련 인터랙티브 요소(폼의 `Input`, 취소 `Button` 등)를 `disabled`로 잠가 중복 요청을 막는다(`form.md` 참고).

### Error (오류)

```
[ 오류 문구 (body, fg.muted 또는 fg.base) ]  ← space.stack-md
[ Button variant=secondary "다시 시도" ]
```

- 오류 문구는 담담한 사실 전달 + 다음 행동 제시(voice-tone `오류` 톤): "일정을 불러오지 못했어요. 잠시 후 다시 시도해 주세요."
- 재시도 `Button`은 기본적으로 `variant="secondary"`를 쓴다 — 오류 자체가 파괴적 행위가 아니라 복구 시도이기 때문이다.
- `variant="danger"`는 오류 안내 문구나 재시도 버튼에 쓰지 않는다. danger는 사용자가 취하는 행동이 파괴적일 때(삭제 확정 등)만 쓰는 것이 원칙이며, "다시 시도"는 파괴적 행동이 아니다.
- 필드 단위 오류(폼 유효성)는 이 섹션이 아니라 `Input`의 `errorMessage`로 처리한다(`form.md` 참고) — 화면 전체를 덮는 오류 블록과 필드 단위 오류를 혼동하지 않는다.
- 네트워크 오류처럼 화면 전체 콘텐츠를 못 불러온 경우만 이 전체 화면형 오류 블록을 쓰고, 일부 데이터만 실패한 경우(예: 적립 내역은 실패, 잔액은 성공)는 해당 섹션에만 국소적으로 작은 오류 안내 + 재시도 버튼을 배치해 나머지 콘텐츠는 그대로 보여준다.

## 반응형

- 세 상태 모두 콘텐츠 영역 안에서 세로 중앙 정렬을 기본으로 하며, 모바일/데스크톱에서 레이아웃 폭만 콘텐츠 영역 폭을 따라간다(별도 반응형 규칙 없음).
- 스켈레톤 개수는 뷰포트에 따라 조정 가능(모바일 2~3개, 데스크톱 그리드라면 그리드 칸 수만큼).
- Empty/Error 블록의 최대 폭을 제한(예: 본문 폭 기준)해 넓은 화면에서 문구가 지나치게 길게 늘어지지 않게 한다.

## 상태 (empty / loading / error)

이 문서 자체가 세 상태를 다루는 문서이므로, 각 상태의 전환 규칙을 정리한다.

- 초기 로딩(loading) → 성공 시 실제 콘텐츠, 결과가 0건이면 empty, 실패하면 error로 전환한다.
- error 상태에서 "다시 시도"를 누르면 다시 loading 상태로 돌아간다(스켈레톤 재노출).
- empty는 "정상적으로 콘텐츠가 없는 상태"이므로 error와 구분한다 — 데이터 fetch 자체가 실패했다면 empty가 아니라 error를 보여준다(빈 목록으로 오인하게 하지 않는다).

## 접근성

- 상태가 바뀌는 콘텐츠 영역(로딩→완료, 로딩→오류, 로딩→빈 상태)에는 상위 컨테이너에 `aria-live="polite"`를 부여해 스크린리더가 전환을 인지하게 한다. 단, 스켈레톤이 노출되는 그 순간 자체까지 안내할 필요는 없고, 최종 상태(콘텐츠/empty/error)로 확정되었을 때 안내되면 충분하다.
- 스켈레톤 블록은 장식 요소이므로 `aria-hidden="true"`로 처리하고, 로딩 중임을 알리는 텍스트는 화면에 보이지 않아도 스크린리더가 읽을 수 있는 요소(예: 시각적으로 숨긴 "일정을 불러오는 중이에요" 텍스트) 하나만 별도로 둔다 — 스켈레톤 블록 개수만큼 반복해서 읽히지 않도록 주의한다.
- `Button`의 `loading` 상태는 `aria-busy="true"`가 자동 적용되므로 중복으로 `aria-live` 문구를 추가하지 않는다.
- 재시도 `Button`은 포커스 가능한 위치(오류 문구 바로 아래)에 두어 Tab 이동만으로 바로 도달 가능해야 한다.
- 색만으로 오류/성공을 구분하지 않는다 — 오류 블록은 항상 텍스트 문구를 동반하고, `Badge`로 상태를 표기하는 경우도 마찬가지로 텍스트 라벨을 항상 함께 노출한다.
