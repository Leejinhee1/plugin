# 핸드오프 문서 (파트/세션 간 릴레이 전달)

작업을 넘길 때 상대가 처음부터 다시 파악하지 않아도 되게 하는 짧은 전달 문서를 만듭니다. mattpocock/skills 의 handoff 기법을 HDS 릴레이 흐름(`docs/user-guide.md` §6)에 맞게 씁니다.

## 용도
- 기획 → 디자인 (설계서 확정 후 신규 컴포넌트/토큰 요청)
- 디자인 → 퍼블 (컴포넌트/토큰 릴리스 후 구현 요청)
- 세션 → 다음 세션 (같은 작업을 다른 세션이 이어받음)

## 규칙
- **중복 금지**: 이미 존재하는 산출물(설계서, `registry.json`, `CHANGELOG.md`, spec.md 등)에 있는 내용은 본문에 옮겨 적지 말고 **경로 참조**로만 넣는다. 핸드오프 문서는 산출물을 대체하지 않고 안내한다.
- **민감정보 제외**: 자격증명, 개인정보, 미확정 내부 논의는 넣지 않는다.
- **짧게**: 받는 쪽이 5분 안에 읽고 다음 행동을 알 수 있는 분량으로 쓴다.

## 산출 형식 (고정 템플릿)

```markdown
# 핸드오프: <기능/작업명>

## 1. 목적 / 받는 파트
무엇을 위해, 누구에게 넘기는지 한 줄로.

## 2. 완료된 것
- <산출물 이름> — `path/to/file` (경로만, 내용 복붙 금지)
- ...

## 3. 결정 사항과 근거
- <결정> — 근거: <원칙/가이드 문서 경로 또는 이유>
- ...

## 4. 미해결 (Open questions)
- <아직 정해지지 않은 것> — 누가/언제 결정하는지 명시

## 5. 받는 파트가 다음에 할 일
1. <구체적 행동> — 사용할 HDS 스킬: `/hds-xxx:yyy`
2. ...

## 6. 주의점
- <함정, 예외, 되돌리기 어려운 결정 등>
```

각 섹션은 비워두지 말고 "해당 없음"이라도 명시합니다. 항목이 실제로 없으면 생략하지 말고 그렇게 적어, 받는 쪽이 "빠뜨린 건지 없는 건지" 헷갈리지 않게 합니다.

## 다음 할 일(§5) 작성 지침
받는 파트가 곧바로 실행할 수 있도록 HDS 슬래시 스킬을 순서대로 명시합니다.
- 디자인이 받는 경우: 신규 컴포넌트 요청이면 `/hds-design:component-catalog`, 토큰 요청이면 `/hds-design:design-tokens`.
- 퍼블이 받는 경우: 구현은 `/hds-publish:component-build` → 배포 전 검토는 `/hds-publish:ui-review` → 접근성 심층 점검은 `/hds-publish:a11y-audit`.
- 세션 간 인계인 경우: 지금까지 실행한 스킬과 다음에 이어서 실행할 스킬을 순서대로.

## 저장 위치
해당 기능 설계서 옆에 `docs/specs/<feature>.handoff.md` 로 저장하는 것을 권장합니다. `/hds-publish:ui-review` 등 후속 스킬이 이 경로를 기본으로 참조합니다.

## 작성 후
- 기획→디자인: 설계서 확정(`/hds-planning:spec-review` 통과) 직후 작성.
- 디자인→퍼블: 컴포넌트/토큰 릴리스(버전 bump) 직후 작성.
- 세션→세션: 작업을 중단하거나 넘기기 직전, 지금까지의 맥락을 요약해 작성.
