# 생성 / 편집 폼 (일정 추가)

새 일정을 추가하거나 기존 일정을 수정하는 폼. 여러 `Input`을 세로로 쌓고, 유효성 검사 후 제출하는 흐름의 기본 패턴.

## 목적

- 사용자가 필요한 정보를 순서대로 입력하고, 실수했을 때 어떤 필드가 문제인지 즉시 알 수 있게 한다.
- 저장 진행 상태와 결과(성공/실패)를 명확히 알려 중복 제출이나 불안을 방지한다.
- 취소 시 입력 중이던 내용을 잃는다는 사실을 사용자가 인지하게 한다(파괴적일 수 있는 취소 흐름은 신중히 다룬다).

## 구성 (컴포넌트 + 레이아웃)

세로 스택 폼. 화면(또는 `Modal` `size="md"`) 안에 배치 가능 — 새 일정 추가처럼 짧은 폼은 Modal 안에, 편집처럼 필드가 많은 폼은 전체 화면에 배치한다.

```
[ Input: label="일정 제목" size=md ]
  ── space.stack-md ──
[ Input: label="날짜" size=md ]
  ── space.stack-md ──
[ Input: label="시간" size=md ]
  ── space.stack-md ──
[ Input: label="장소" size=md, helperText="선택 사항이에요." ]
  ── space.stack-md ──
[ 액션 영역: Button(secondary,"취소") + Button(primary,"저장") ]
```

- 필드 간 간격은 `space.stack-md`(Input 스펙 기본 라벨-필드-도움말 간격 `space.stack-sm`과 구분: 필드 "묶음" 사이는 md, 한 필드 내부 라벨/도움말은 sm).
- 각 `Input`은 `label`을 반드시 지정한다(`placeholder`는 라벨 대용 금지). 선택 입력(예: 장소, 메모)은 `helperText`로 "선택 사항이에요." 등을 명시해 필수 여부를 알린다.
- `size`는 폼 전체에서 통일한다(기본 `md`). 화면 밀도가 높은 Modal 내부 폼은 `sm`도 가능하나 한 폼 안에서 섞지 않는다.
- 액션 영역은 우측 정렬, 두 `Button` 사이 간격 `space.stack-sm`.
  - 취소: `variant="secondary"`.
  - 저장/제출: `variant="primary"`, 폼당 1개만(primary 2개 이상 배치 금지 원칙).
  - 폼이 파괴적 삭제를 포함한다면(예: 편집 화면의 "일정 삭제") 별도로 분리된 `variant="danger"` 버튼을 두고, 주요 저장 액션과 시각적으로 명확히 구분되는 위치(예: 하단 별도 구역)에 둔다.
- 폼 전체 바깥 여백: `space.inset-lg`(전체 화면) 또는 Modal 사용 시 Modal 자체의 `space.inset-lg` 패널 여백을 그대로 활용.

### 예문 (voice-tone 준수)

- 필드 라벨: "일정 제목", "날짜", "시간", "장소"
- helperText: "선택 사항이에요."
- 저장 버튼: "저장"
- 취소 버튼: "취소"
- 저장 성공 후 안내(폼 바깥 토스트 등 별도 영역): "일정을 추가했어요."

## 반응형

- 모바일: 필드 폭 100%, 세로 1열 스택. 액션 영역은 하단 고정(sticky) 또는 폼 마지막에 배치하되, 화면이 길어 스크롤이 필요할 경우 저장 버튼이 항상 도달 가능해야 한다.
- 태블릿/데스크톱: 관련 필드(예: 날짜 + 시간)를 가로로 2열 그리드에 배치할 수 있다. 이때도 필드 간 가로 간격은 `space.stack-md`를 사용하고, 라벨 정렬은 필드마다 개별 유지(Input이 라벨을 내장하므로 별도 정렬 컴포넌트 불필요).
- 좁은 화면에서 Modal로 폼을 열 때는 `size="md"`가 콘텐츠보다 작아지지 않는지 확인하고, 필드가 4개를 넘으면 전체 화면 폼으로 전환하는 편이 낫다.

## 상태 (empty / loading / error)

- **초기 상태**: 신규 생성은 모든 필드가 빈 값, 편집은 기존 값이 채워진 상태로 시작한다. 편집 폼이 원본 데이터를 아직 못 불러왔다면 Input 자리에 스켈레톤을 노출하고 필드는 `disabled`로 잠근다.
- **유효성 흐름**:
  1. 제출 시점(또는 필드 이탈 시) 검증. 실시간 키 입력마다 오류를 띄우지 않는다(과도한 방해 금지).
  2. 문제가 있는 필드에 `errorMessage`를 채운다. 예: `errorMessage="일정 제목을 입력해 주세요."`, `errorMessage="종료 시간은 시작 시간 이후여야 해요."`
  3. `errorMessage`가 있으면 자동으로 `invalid` 상태(테두리·포커스 링이 `color.feedback.danger`)가 되므로 `invalid`를 별도로 세팅할 필요는 없다.
  4. 여러 필드에 오류가 있으면 모두 동시에 표시하고, 첫 번째 오류 필드로 포커스를 이동시켜 재입력을 돕는다.
  5. 사용자가 값을 고치기 시작하면 해당 필드의 오류를 즉시 해제한다(값이 유효해질 때까지 남겨두지 않는다).
- **저장 중(loading)**: 제출 `Button`에 `loading={true}`(라벨은 "저장" 유지, 스피너로 진행 중임을 표시하고 `aria-busy="true"` 자동 적용). 저장 중에는 취소 버튼과 모든 `Input`을 `disabled`로 잠가 중복 제출·값 변경을 막는다.
- **저장 실패(error)**: 서버 오류 등으로 저장이 실패하면 필드별 오류가 아니라 폼 전체 오류이므로, 액션 영역 위에 오류 안내 영역을 추가한다.
  - 문구: "일정을 저장하지 못했어요. 잠시 후 다시 시도해 주세요."
  - 저장 `Button`은 다시 클릭 가능한 상태(`loading=false`)로 돌아오고, 입력했던 값은 그대로 유지한다.

## 접근성

- 포커스 순서는 시각적 순서와 동일하게: 첫 번째 `Input` → 이후 필드 순 → 취소 → 저장. 폼 진입 시 첫 필드에 자동 포커스하는 것을 권장(단, Modal 안에서는 Modal 자체의 포커스 이동 규칙을 따른다).
- 오류 메시지 영역(필드별 `errorMessage`)은 `aria-describedby`로 각 `Input`과 연결되어 있어야 하며(Input 스펙 기본 동작), 색만으로 오류를 전달하지 않는다.
- 제출 시 여러 필드에 오류가 발생하면, 폼 상단 또는 첫 오류 필드 인근에 `aria-live="polite"` 영역을 두어 "입력 내용을 확인해 주세요" 같은 요약을 스크린리더가 즉시 인지하게 한다.
- 저장 중(`loading`) 상태는 `Button`의 `aria-busy="true"`로 전달되며, 저장 후 화면 전환이 일어나면 포커스를 다음 화면의 논리적 시작 지점(예: 방금 추가된 일정 카드)으로 명시적으로 옮긴다.
- 필수/선택 여부는 시각 스타일(색상)만으로 구분하지 않고 `helperText`(예: "선택 사항이에요.")로 텍스트로도 안내한다.
