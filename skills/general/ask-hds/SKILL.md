# Ask HDS

스킬을 전부 외울 필요는 없습니다 — 이 스킬에 물어보세요.

이 스킬은 **일을 직접 하지 않습니다.** 설계서를 쓰지도, 토큰을 고치지도, 코드를 만들지도 않습니다. 상황을 듣고 → 맞는 스킬(들)과 순서를 알려주고 → 실행은 그 스킬에 넘깁니다. 이미 쓸 스킬을 알고 있다면 라우터를 거치지 말고 바로 호출하세요.

**플로우**란 스킬 하나가 아니라 스킬들을 지나는 경로입니다. HDS의 일은 대부분 하나의 **메인 플로우**(기능 → 배포)를 타고, 나머지는 **정비 레인** 아니면 **단독 스킬**입니다. 질문을 받으면 스킬 이름 하나가 아니라 "지금 어느 플로우의 어느 단계인지"로 답하세요.

## 첫 분기: 시스템을 바꾸는가, 시스템을 쓰는가

| 하려는 일 | 작업 위치 | 레인 |
| :-- | :-- | :-- |
| 토큰·가이드·컴포넌트·브랜드 규범 **자체를 고친다** | HDS 저장소 | 정비 레인 ↓ |
| 시스템으로 **기획·프로토타입·구현을 한다** | 내 제품 저장소 | 메인 플로우 ↓ |

이 구분이 흔들리면 사고가 납니다. 제품 화면을 만들다 "이 색만 바꾸고 싶다"가 나오면 그건 쓰는 일이 아니라 **바꾸는 일** — 화면에서 우회(하드코딩)하지 말고 정비 레인으로 넘어와야 합니다.

## 메인 플로우: 기능 → 배포

기획이 시작해 퍼블이 끝내는 표준 경로.

1. **`/hds:product-spec`** — 설계서 작성. 화면을 자연어가 아니라 **HDS 컴포넌트·토큰 이름으로** 명세합니다. 모든 파생물(프로토타입·구현)의 출발점.
2. **분기 — 필요한 컴포넌트가 카탈로그에 없는가?** 그 자리에서 만들지 말고, 설계서에 "신규 컴포넌트 후보"로 표시한 뒤 정비 레인의 `/hds:component-catalog` 로 넘깁니다. 추가가 릴리스되면 다시 이 지점으로 복귀.
3. **`/hds:prototype`** — 설계서를 실제 HDS 컴포넌트·토큰으로 조립한 동작 프로토타입으로. 리뷰·의사결정용이고 데이터는 목업.
4. **퍼블 3연타** (내 제품 저장소에서, 이 순서로):
   1. **`/hds:token-export`** — `tokens.css`·Tailwind preset 생성. 항상 컴포넌트 설치보다 먼저.
   2. **`/hds:component-build`** — 레지스트리 컴포넌트를 프로젝트에 설치(shadcn 방식).
   3. **`/hds:a11y-audit`** — 배포 전 접근성(WCAG AA) 점검.
5. 검수가 필요하면 어느 단계에서든 **`hds:design-reviewer` 에이전트** — 토큰 준수·가이드 부합·접근성을 심층 리뷰합니다(파일은 수정하지 않음).

## 정비 레인: 디자인 시스템 자체를 고친다

HDS 저장소에서 합니다. 모든 변경은 `CHANGELOG.md` + version bump 동반.

- **`/hds:design-tokens`** — 색·타이포·간격·모션 값의 조회/추가/수정. 리브랜딩·다크테마·계열사 테마도 여기(core 토큰만 교체하면 전체가 따라옴).
- **`/hds:component-catalog`** — 컴포넌트 조회와 신규 추가(spec+code+usage 3종 + registry 등록). "무슨 컴포넌트 있어?"도 이 스킬.
- **`/hds:design-guide`** — 원칙·규범 문서의 조회/갱신. 시안이나 결정이 가이드에 맞는지 원칙 번호를 근거로 검토.
- 마무리: **`hds:design-reviewer`** 검수 → 릴리스 → 각 팀이 `/plugin update hds@hds` 로 수신.

## 헷갈리는 짝 — 이름이 비슷해도 방향이 다르다

- **`component-catalog` vs `component-build`** — catalog는 **시스템에** 컴포넌트를 넣습니다(HDS 저장소). build는 시스템의 컴포넌트를 **내 프로젝트에** 설치합니다(제품 저장소). 넣는 쪽과 받는 쪽.
- **`design-tokens` vs `token-export`** — design-tokens는 **원본**(`tokens/*.json`)을 고칩니다. token-export는 원본에서 **파생물**(`tokens.css` 등)을 재생성합니다. 원본을 고쳤으면 export를 다시 돌려야 반영되고, 파생물을 손으로 고치는 선택지는 없습니다.
- **`prototype` vs `component-build`** — prototype은 의사결정용 목업(버려도 됨), component-build는 프로덕션 코드. 단, 프로토타입이 HDS를 지켰다면 퍼블 단계는 재작성이 아니라 정리로 끝납니다.

## 단독 스킬

- **`/hds:brand-visual`** — 키비주얼·모션·영상 등 브랜드 자산의 기획/검수. 제품 UI와 같은 토큰 언어(색·듀레이션·이징)를 쓰게 합니다.
- **`/hds:figma-bridge`** — 코드 토큰 ↔ Figma Variables 동기화(Figma MCP 연결 필요). 충돌 시 **코드가 진실**.
- **`/hds:a11y-audit`** — 메인 플로우 밖에서도 아무 때나. "이 색 조합 대비 괜찮아?" 하나만 검사할 때도 이 스킬.

## 업데이트를 받았을 때 (퍼블)

"HDS x.y.z 릴리스" 공지가 오면: `/plugin update hds@hds` → `/hds:token-export` 재생성 → 바뀐 컴포넌트만 `/hds:component-build` 재실행. 산출물을 손으로 고친 적이 없다면 충돌도 없습니다.
