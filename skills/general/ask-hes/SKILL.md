# Ask HES

스킬을 전부 외울 필요는 없습니다 — 이 스킬에 물어보세요.

이 스킬은 **일을 직접 하지 않습니다.** 설계서를 쓰지도, 토큰을 고치지도, 코드를 만들지도 않습니다. 상황을 듣고 → 맞는 스킬(들)과 순서를 알려주고 → 실행은 그 스킬에 넘깁니다. 이미 쓸 스킬을 알고 있다면 라우터를 거치지 말고 바로 호출하세요.

**플로우**란 스킬 하나가 아니라 스킬들을 지나는 경로입니다. HES의 일은 대부분 하나의 **메인 플로우**(기능 → 배포)를 타고, 나머지는 **정비 레인** 아니면 **단독 스킬**입니다. 질문을 받으면 스킬 이름 하나가 아니라 "지금 어느 플로우의 어느 단계인지"로 답하세요.

## ⚠️ 지금 실행 가능한 스킬 (라우팅 규칙)

HES는 아직 개발 중이며, **아래 4개만 설치·실행됩니다**:

| 실행 가능 | 용도 |
| :-- | :-- |
| `/hes:ask-hes` | 이 라우터 |
| `/hes:mcp-connectors` | 커넥터·MCP 현황/관리 |
| `/hes:test-script` | UI 기획서 → QA 테스트 시나리오 |
| `/hes:spec-lookup` | 사내 설계서 저장소에서 화면·정책 조회 |

나머지는 아래 문서에서 **`준비중`** 으로 표시되며 `.claude-plugin/plugin.json` 의 `_disabledSkills` 에 보관돼 있습니다 — 파일은 있지만 로드되지 않습니다.

**라우팅할 때 반드시:**
- 준비중 스킬을 `/hes:xxx` 슬래시 커맨드 형태로 안내하지 않는다. 호출해도 없는 커맨드다.
- 사용자의 상황이 준비중 단계에 해당하면 → **어느 단계인지 알려주고, 그 스킬이 아직 준비중임을 명시하고, 지금 할 수 있는 대안**(직접 작업 / `design-system/` 소스 직접 참조 / 실행 가능한 스킬로 우회)을 제시한다.
- 없는 스킬이 있는 척하지 않는다.

## 첫 분기: 시스템을 바꾸는가, 시스템을 쓰는가

| 하려는 일 | 작업 위치 | 레인 |
| :-- | :-- | :-- |
| 토큰·가이드·컴포넌트·브랜드 규범 **자체를 고친다** | HES 저장소 | 정비 레인 ↓ |
| 시스템으로 **기획·프로토타입·구현을 한다** | 내 제품 저장소 | 메인 플로우 ↓ |

이 구분이 흔들리면 사고가 납니다. 제품 화면을 만들다 "이 색만 바꾸고 싶다"가 나오면 그건 쓰는 일이 아니라 **바꾸는 일** — 화면에서 우회(하드코딩)하지 말고 정비 레인으로 넘어와야 합니다.

## 메인 플로우: 기능 → 배포

기획이 시작해 퍼블이 끝내는 표준 경로. **현재 이 플로우의 스킬은 전부 준비중입니다** — 단계 진단에는 쓰되, 실행 안내는 하지 마세요.

1. **product-spec** `준비중` — 설계서 작성. 화면을 자연어가 아니라 **HES 컴포넌트·토큰 이름으로** 명세합니다. 모든 파생물(프로토타입·구현)의 출발점.
2. **분기 — 필요한 컴포넌트가 카탈로그에 없는가?** 그 자리에서 만들지 말고, 설계서에 "신규 컴포넌트 후보"로 표시한 뒤 정비 레인의 **component-catalog** `준비중` 로 넘깁니다. 추가가 릴리스되면 다시 이 지점으로 복귀.
3. **prototype** `준비중` — 설계서를 실제 HES 컴포넌트·토큰으로 조립한 동작 프로토타입으로. 리뷰·의사결정용이고 데이터는 목업.
4. **퍼블 3연타** (내 제품 저장소에서, 이 순서로) — 셋 다 `준비중`:
   1. **token-export** — `tokens.css`·Tailwind preset 생성. 항상 컴포넌트 설치보다 먼저.
   2. **component-build** — 레지스트리 컴포넌트를 프로젝트에 설치(shadcn 방식).
   3. **a11y-audit** — 배포 전 접근성(WCAG AA) 점검.
5. 검수가 필요하면 어느 단계에서든 **`hes:design-reviewer` 에이전트** — 토큰 준수·가이드 부합·접근성을 심층 리뷰합니다(파일은 수정하지 않음). **에이전트는 스킬과 별개로 지금도 사용 가능합니다.**

> 준비중 단계를 만났을 때의 대안: 설계서·프로토타입·토큰 CSS는 스킬 없이도 `design-system/` 의 `tokens/`·`components/`·`usage/screens/` 를 직접 읽어 수동으로 진행할 수 있습니다. 컴포넌트 설치는 스킬 대신 CLI(`npx hes add <name>`)가 이미 동작합니다.

## 정비 레인: 디자인 시스템 자체를 고친다

HES 저장소에서 합니다. 모든 변경은 `CHANGELOG.md` + version bump 동반. **이 레인의 스킬도 전부 준비중** — 해당 작업은 지금은 소스를 직접 편집합니다.

- **design-tokens** `준비중` — 색·타이포·간격·모션 값의 조회/추가/수정. 리브랜딩·다크테마·계열사 테마도 여기(core 토큰만 교체하면 전체가 따라옴). → 지금은 `design-system/tokens/*.json` 직접 편집.
- **component-catalog** `준비중` — 컴포넌트 조회와 신규 추가(spec+code+usage 3종 + registry 등록). "무슨 컴포넌트 있어?"도 이 스킬. → 지금은 `design-system/components/registry.json` 조회 / 해당 폴더 직접 추가.
- **design-guide** `준비중` — 원칙·규범 문서의 조회/갱신. 시안이나 결정이 가이드에 맞는지 원칙 번호를 근거로 검토. → 지금은 `design-system/guidelines/` 직접 읽기.
- 마무리: **`hes:design-reviewer`** 검수(사용 가능) → 릴리스 → 각 팀이 `/plugin update hes@hes` 로 수신.

## 헷갈리는 짝 — 이름이 비슷해도 방향이 다르다

- **`component-catalog` vs `component-build`** — catalog는 **시스템에** 컴포넌트를 넣습니다(HES 저장소). build는 시스템의 컴포넌트를 **내 프로젝트에** 설치합니다(제품 저장소). 넣는 쪽과 받는 쪽.
- **`design-tokens` vs `token-export`** — design-tokens는 **원본**(`tokens/*.json`)을 고칩니다. token-export는 원본에서 **파생물**(`tokens.css` 등)을 재생성합니다. 원본을 고쳤으면 export를 다시 돌려야 반영되고, 파생물을 손으로 고치는 선택지는 없습니다.
- **`spec-lookup` vs `product-spec`** — spec-lookup 은 **이미 있는 설계서를 읽습니다**(다른 저장소, 읽기 전용). product-spec 은 **새 설계서를 씁니다**(내 저장소). 읽는 쪽과 쓰는 쪽입니다. "설계가 어떻게 돼 있지?"는 lookup, "설계를 정하자"는 spec.
- **`spec-lookup` vs `test-script`** — 둘 다 확정된 기획서를 입력으로 받지만, lookup 은 **저장소의 마크다운 설계서를 조회**하고 test-script 는 **Figma·PDF 기획서를 파싱해 QA 시나리오를 만듭니다.** 묻는 것과 뽑는 것.
- **`prototype` vs `component-build`** — prototype은 의사결정용 목업(버려도 됨), component-build는 프로덕션 코드. 단, 프로토타입이 HES를 지켰다면 퍼블 단계는 재작성이 아니라 정리로 끝납니다.

## 단독 스킬

지금 쓸 수 있는 것:

- **`/hes:test-script`** — 확정된 UI 기획서(Figma URL·PDF·이미지·이미지 폴더)를 파싱해 QA 테스트 시나리오를 만들고 클립보드/CSV/Google Sheets 로 출력. 입력이 HES 설계서일 필요가 없어(외부 팀 Figma·PDF도 가능) 메인 플로우의 단계가 아니라 단독 스킬입니다. 화면 정의가 확정된 뒤라면 언제든. Figma 입력은 `figma-bridge` 와 달리 **읽기 전용**입니다 — 토큰 동기화가 아니라 스펙 텍스트 추출.
- **`/hes:spec-lookup`** — **우리 팀 설계서 저장소**에서 화면·정책을 찾아 근거와 함께 답합니다. **전제가 있습니다** — 설계서가 마크다운으로 Git 저장소에 있고, 묻는 사람이 그 저장소를 읽을 수 있어야 합니다(플러그인은 어느 저장소도 기본값으로 갖지 않습니다). 그 전제가 없는 팀에는 이 스킬을 권하지 마세요 — Figma·PPT 기획서라면 `/hes:test-script` 쪽입니다. "이 화면 어떻게 동작해?", "화면ID CRD_202가 뭐야?" 류 질문. 설계서 본문은 플러그인이 아니라 그 저장소에만 있고, 스킬은 매 호출 최신으로 동기화해 읽는 **얇은 어댑터**입니다. 대상 저장소는 `.hes/spec-source.json`·`HES_SPEC_REPO` 로 지정하며(읽기 권한 필요), 조회 절차·응답 규율은 그 저장소의 `docs/agents/spec-lookup.md` 가 정합니다.
- **`/hes:mcp-connectors`** — 플러그인이 제공(번들)하는 커넥터·MCP 서버의 공식 목록·현재 연결 현황·커넥터 등록/관리. "무슨 MCP 써?", "Figma 연결됐어?" 류 질문. Figma 서버는 플러그인이 등록하므로 Figma 앱 Dev Mode 만 켜면 연결됨.

준비중:

- **brand-visual** `준비중` — 키비주얼·모션·영상 등 브랜드 자산의 기획/검수. 제품 UI와 같은 토큰 언어(색·듀레이션·이징)를 쓰게 합니다. → 지금은 `design-system/brand/` 직접 참조.
- **figma-bridge** `준비중` — 코드 토큰 ↔ Figma Variables 동기화(Figma MCP 연결 필요). 충돌 시 **코드가 진실**.
- **a11y-audit** `준비중` — 메인 플로우 밖에서도 아무 때나. "이 색 조합 대비 괜찮아?" 하나만 검사할 때도 이 스킬. → 지금은 `design-system/guidelines/color.md` 기준으로 수동 검토.

## 업데이트를 받았을 때 (퍼블)

"HES x.y.z 릴리스" 공지가 오면: `/plugin update hes@hes` → token-export 재생성 → 바뀐 컴포넌트만 component-build 재실행. 산출물을 손으로 고친 적이 없다면 충돌도 없습니다.

두 스킬이 `준비중`인 동안에는 CLI 로 대체합니다: `npx hes list` 로 변경분 확인 → `npx hes add <name>` 재실행(토큰 CSS 포함).
